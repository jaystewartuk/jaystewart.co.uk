Case study

Beckon

A remote inbox for coding agents and long jobs. See when one needs you; answer from your phone.

The problem

Four Hacker News threads described the same gap: agents and long jobs run on machines nobody is watching, then stall waiting for a decision. The bet: one inbox across machines, and a push when something is blocked.

I wrote the spec first, including the security model and what not to build: no remote terminal, no free typing.

One tap, made safe

  • Content is end-to-end encrypted; the server only routes ciphertext.
  • Devices pair by comparing a six-word safety code.
  • The phone signs a choice. The host checks signature, trust and freshness before typing anything.
  • Stale, replayed or read-only responses are rejected, and every outcome is audited.

Devices never send keystrokes, so a compromised server can't type into your terminal.

The whole path

A Go helper runs the command in a pseudo-terminal and reads its status (OSC 7501), or spots known prompts. Next.js, WebSockets and Postgres keep sessions live; the web app pairs, decrypts and pushes. Tests cover pass-through, crypto between Go and TypeScript, server tampering and end-to-end flows.

Production on one small VM

Cloud Run was the wrong shape: helpers hold connections open so it's rarely idle, it cuts connections every hour, and cold starts delay alerts. Now it's one VM for a few euros a month.

  • Deploys: release over SSH, migrate, health check. Rollback takes about 20 seconds.
  • Hardening: key-only SSH, closed between sessions; only ports 80 and 443; unprivileged, read-only containers.
  • Backups: nightly, encrypted, to storage the server can't delete. Restore rehearsed.
  • Monitoring: an outside uptime check, plus a dead man's switch.

Billing is live: free, or Pro at $8 a month. The code is public and self-hostable with Docker Compose.

Next

No outside users yet. Next: put it in front of developers who run agents across machines, see where setup and trust break, and find out if it's worth paying for.
